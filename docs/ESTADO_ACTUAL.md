## 🔴 Bloqueante actual

**No son llaves mezcladas entre producción y Sandbox** — eso se detectó y
se corrigió dentro de esta misma sesión (2026-10-04); las cuatro llaves de
Wompi en `.env.local` ya están verificadas como Sandbox (`pub_test_`,
`test_integrity_`, `test_events_`, `prv_test_`), consistentes entre sí.

El bloqueante real: al abrir el widget de Wompi desde `/dashboard/checkout`,
Wompi devuelve un **403 de CloudFront** ("Request blocked... Generated by
cloudfront"). Se descartó que sea algo de este repo:

- La URL que arma el widget se revisó completa — todos los parámetros
  (`reference`, `amount-in-cents`, `currency`, `redirect-url`,
  `signature:integrity`) están bien formados y coinciden con lo que calcula
  `/api/wompi/signature`.
- Se probó pegando esa URL completa directo en el navegador, **fuera** de
  la app — el mismo 403 de CloudFront aparece igual, con un Request ID
  distinto cada vez. Esto confirma que el bloqueo ocurre en la
  infraestructura de Wompi (o en la red/IP de quien prueba), antes de que
  la petición llegue a la lógica de la aplicación de Wompi que validaría
  la firma.
- Se descartó un bloqueador de anuncios del navegador (se probó con
  AdBlock desactivado, mismo resultado).

**Próximos pasos sugeridos** (no son cambios de código):
1. Probar desde otra red (datos móviles, sin VPN) para descartar que la IP
   esté marcada por el WAF de Wompi.
2. Revisar en comercios.wompi.co que la cuenta/modo Sandbox esté
   completamente activado, sin pasos pendientes.
3. Si persiste, escribir a soporte de Wompi con los Request ID recogidos
   durante las pruebas (quedan en el historial de chat de esta sesión, no
   en este archivo).

## Pendiente de confirmar

  `pg_cron` de vencimiento de suscripciones): no quedó confirmado si ya se

  cron de vencimiento está corriendo.
- **Formato de las llaves de Supabase en `.env.local`**: en algún punto
  cambiaron de el formato nuevo (`sb_publishable_...` / `sb_secret_...`) al
  formato JWT legacy (`eyJhbGci...`, con `role: anon` / `role: service_role`
  en el payload). El `ref` de ambos JWT coincide con el proyecto correcto y
  el código funciona igual con cualquiera de los dos formatos, pero nunca
  se confirmó si el cambio fue intencional (¿se rotaron las llaves en el
  dashboard de Supabase?) o un descuido.

## Decisiones abiertas conocidas (sin resolver a propósito)

- **Decisión 16** de `ARCHITECTURE.md`: como el código de un cupón es
  público y compartido, el dueño depende de que el nombre/teléfono que el
  cliente da en el local coincida con el que dio al reservar. El buscador
  de `/dashboard/cupones` (Fase 7) solo mira los últimos 50 leads, sin
  paginación ni filtro por fecha.
- **Límite de frecuencia de `/api/leads`**: en memoria (`lib/rate-limit.ts`),
  best-effort, se reinicia en cada arranque en frío. Reemplazar por Upstash
  Ratelimit si el tráfico real del piloto lo justifica.
- **Bronce** (tercer nivel de calidad): descartado para el MVP a propósito;
  si hiciera falta, es una migración aparte sobre `catalogo_sellos`/
  `barberias.estado_sello_check`.
